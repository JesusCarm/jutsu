# CapRover deployment

Pushes to `main` run type checking and tests, build an Angular production bundle inside a multi-stage Docker build, and publish a commit-tagged image to GitHub Container Registry (GHCR). The workflow smoke-tests the published image, asks CapRover to deploy its immutable digest, and checks that the public app serves the requested commit and a healthy response. Pull requests only run verification. The workflow can also be started manually on `main`.

The image supports `linux/amd64` and `linux/arm64`. Its final stage contains Nginx and the static application; Node.js and source build dependencies stay in the build stage. `captain-definition` provides the standard CapRover Dockerfile configuration for optional source deployments. The GitHub workflow uses the prebuilt-image deployment mode instead, so Angular compilation runs in GitHub rather than on the VPS.

## One-time CapRover setup

1. Create an application, for example `jutsu`. Set its **Container HTTP Port** to **80**. No persistent directories or host port mappings are needed.
2. Point the desired subdomain, for example `jutsu.gipsygames.com`, at the VPS. Add that domain to the app, enable HTTPS, and enable HTTPS redirection.
3. In the app's Deployment tab, enable an **app deployment token**. Use this token rather than the CapRover dashboard password.
4. Make sure CapRover can pull the image from GHCR. New GHCR packages are private by default. Either configure GHCR registry credentials in CapRover using a GitHub personal access token (classic) with `read:packages`, or make the published package public and rerun the workflow. The GitHub runner's registry login does not grant CapRover pull access.

CapRover's **Method 3: Deploy from GitHub/Bitbucket/GitLab** is a separate source deployment route: its repository webhook makes the VPS fetch and build the source. Leave that method unconfigured when using this workflow, which builds the image in GitHub Actions and deploys through the app token. Enable only one automatic deployment route for the app to avoid deploying twice on each push.

### CapRover proxy and application Nginx

Keep CapRover's default Nginx template in its dashboard. It terminates HTTPS, manages certificate challenges, and proxies requests to the application's **Container HTTP Port**, which must be **80**. Its generated `$upstream` already points at the application container, so no manual upstream or proxy location changes are needed for this app.

The separate `docker/nginx.conf` is installed inside the application image. It serves the compiled Angular files and handles route fallback, localized `/es/` HTML, crawler discovery files, caching, `/runtime-config.js`, `/build-info.json`, and `/healthz`. Keep those rules in the container; do not paste them over CapRover's proxy template. The container uses plain HTTP on its internal Docker network, with public TLS handled by CapRover. See [SEO and indexing](seo.md) for canonical URLs, static HTML generation, and Search Console verification.

## GitHub configuration

Under **Settings → Secrets and variables → Actions**, add these repository variables:

| Variable | Example | Purpose |
| --- | --- | --- |
| `CAPROVER_SERVER` | `https://captain.example.com` | HTTPS URL of the CapRover dashboard |
| `CAPROVER_APP_NAME` | `jutsu` | Exact CapRover application name |
| `APP_URL` | `https://jutsu.gipsygames.com` | Public HTTPS URL used to verify the release |

Add this repository secret:

| Secret | Value |
| --- | --- |
| `CAPROVER_APP_TOKEN` | App deployment token generated by CapRover |

Image publication uses the workflow's automatic `GITHUB_TOKEN` with `packages: write`. No separate push credential is needed. Image repositories are derived from the lowercase GitHub repository name, for example `ghcr.io/jesuscarm/jutsu`. Each image is tagged with the full Git commit SHA, and CapRover receives its immutable digest.

If the package already exists, make sure it is linked to this repository and allows this repository's Actions to write it. Allow the pinned third-party actions in repository/organization Actions settings if restrictions are enabled.

The CapRover action initially reports that deployment was accepted. The following step polls `/build-info.json` and `/healthz` to verify the actual release. A failure there requires checking the CapRover logs, domain/HTTPS configuration, registry access, and HTTP port; it does not automatically roll back a release.

## Google Analytics configuration

Set this in **CapRover → application → App Configs → Environment Variables**:

```dotenv
GA_MEASUREMENT_ID=G-YOURMEASUREMENTID
```

Use the real GA4 measurement ID. Leave the value empty or omit it to disable Analytics. Apply the environment change so CapRover restarts the container. No rebuild is required.

The Nginx entrypoint validates the value and generates `/runtime-config.js` when the container starts. It accepts only an empty value or `G-` followed by uppercase letters and digits. Invalid values stop container startup instead of generating executable JavaScript. The response is served with `Cache-Control: no-store`.

The real value is not committed, passed to GitHub Actions, or embedded in the image. The browser must receive the measurement ID when Analytics is configured, so it remains visible on the published site. Do not put Google private API credentials in this configuration.

Development builds always disable Analytics. In production, a configured ID enables a consent banner with equal accept/reject controls. Google is loaded only after acceptance. The choice is saved in local storage; the footer's Analytics preferences button allows it to be changed. Rejecting a previous acceptance updates consent and disables further collection for this measurement ID. Advertising consent stays denied. The app does not explicitly send squad or ninja fields as Analytics events; review the stream's enhanced measurement settings in Google Analytics before enabling additional automatic collection.

For any static hosting outside Docker, the committed runtime config keeps Analytics disabled unless deployment generates an appropriate replacement file. Node `.env` loading is not required: Docker/CapRover provide the container's environment directly.

## Local Docker check

Run the automated container check before pushing:

```bash
npm run test:docker
```

This requires Docker daemon access, Bash, curl, jq, and Git. It builds `jutsu:local-test` with the current commit, starts a temporary container on a random loopback port, and checks startup, health, build metadata, runtime configuration, Angular route fallback, missing assets, localized HTML, and crawler discovery files and content types. The container is removed after the check; the local image remains available.

To keep a container running for manual inspection:

```bash
cp .env.example .env
# Optionally set GA_MEASUREMENT_ID in .env.
docker build -t jutsu:local .
docker run --rm --env-file .env -p 8080:80 jutsu:local
```

Open `http://localhost:8080`. The `.env` file is ignored by Git and excluded from the Docker build context. It is only passed to the running container.

The Nginx configuration provides Angular route fallback, real 404 responses for missing resources, noncached runtime config/build metadata, and long-lived caching for compiled JS/CSS. CapRover handles the public TLS connection.
